#### K3. 工坊第二輪修正 —— ✅ 2026-10-04 使用者回報後完成

使用者回報五點，其中第一點是**我造成的真 bug**：

4. **「同一份美食只能保留一個…」改為邏輯** —— 不再寫成文字，改為 `detectDelicacyConflicts()`
   偵測，衝突時**在該組合上顯示紅格警告**。

#### K6. 卡牌大師牌組 —— ✅ 2026-10-04 完成（分析報告順位 6）

- `detectSets()` —— 8 種效果（7 個基本 + 禁忌君王），回傳**所有**符合者（原書要求玩家選一個）

**UI** `components/companions/AceOfCardsTable.jsx`：花色對應設定、牌庫／手牌／棄牌堆計數、
點擊選牌、符合效果清單（多個時要求選一個）、結算（付 MP → 打出 → 補抽）、再調度、衝突開始／結束。

### L. 資料層收斂與既有缺陷 —— ✅ 2026-10-04 完成（階段 0）

**背景**：使用者要求「全團登入房間、HP/MP 即時同步」的連線功能。動工前先做前置：把散落的

#### L1. 已修的 bug：NPC 檔案庫三鍵不一致

**症狀**：戰鬥追蹤器的「從怪物庫派兵」永遠是空的；全站備份也備不到真正的 NPC 庫。

**根因**：NPC 檔案庫同時存在三個互不相通的鍵——

### N. 職業技能改數值 ＋ 免費增益 ＋ 跑團卡數值構成公式（2026-10-05）

使用者提出三個問題：① 有沒有哪些職業技能會改變數值（HP／MP），點選後是否真的反映在角色體質上；
② 每個職業都有的免費增益是否真的有造成影響；③ 跑團卡上每個角色體質要能點開看公式，

#### N1. 研究結論（官方五本原書全文掃描，非抽樣）

| 問題 | 結論 |
|---|---|
| 會永久改變數值上限的職業技能 | **全 35 職只有 2 個**：守護者【不動要塞】`SL × 3`（Core p.199）、博學士【集中】`SL × 3`（Core p.201）。Playtest 版兩者皆 `SL × 5`、上限 4 級（三份材料 p.31 逐字相同） |

#### N4. 數值構成公式的設計（使用者裁定：就地展開面板）

- **呈現**：點擊數值 → 在該數值下方展開面板。每一項**小字在上、數值在下**，
  小字說明這筆數字的身分；`kind` 決定配色（base／level／class／skill／equip／heroic／quirk／status 八色）。
- **覆蓋**：跑團卡（HP／MP／IP／危機門檻／物防／魔防／先攻／四屬性）、角色卡（HP／MP／IP／物防／魔防／先攻）。

### O. `resources/` 版權曝險的徹底清除（2026-10-05，§I 結案）

#### O1. 問題的真相：`.gitignore` 對已推送的歷史完全無效

`resources/`（106 檔／92 MB：官方原書 PDF 節錄 ＋ 他人漢化）曾在 2026-10-04 被 `git rm -r --cached`
並加入 `.gitignore`。當時的記載是「已移出版控，但仍在 git history」——**這句話被讀成了「已經處理好了」，
但實際風險完全沒有降低**：

| 層 | 2026-10-05 複驗結果 |
|---|---|
| 工作樹 / 索引 | ✅ 乾淨（`git ls-files resources` = 0） |
| `.gitignore` | ✅ 有排除（`.gitignore:35`） |
| **歷史層** | ❌ 116 個路徑仍在 **3 個已推送的 commit** 裡：`1a17f7f`（初始 commit）、`aad5241`、`1d84a67` |

GitHub API 實測：repo **public**、`size` 76 MB（與本地 `.git` 77.5 MB 相符，證明 blob 確實在雲端）、
`forks_count: 0`、`gh-pages` 分支 0 筆。

> **教訓**：`git rm --cached` ＋ `.gitignore` 只防止**未來**再被追蹤，對**已經推出去的歷史**毫無作用。
> 公開 repo 的「移除敏感檔案」只有一條路：**改寫歷史 ＋ force push**。
> 記載這種狀態時必須寫清楚「工作樹已清 / 歷史未清」，否則會被讀成「已經安全了」。

#### O2. 執行方式（使用者裁定：先提交 → 改寫 → force push）

1. **備份**：`git clone --mirror . scratch/pre-purge-backup.git`（保留改寫前的完整歷史，含 116 個物件）。
   `scratch/` 已列 `.gitignore`，備份不會被推上去。
2. **提交未完成的工作**（`filter-branch` 要求乾淨工作樹）。
3. **改寫**：`git filter-branch --index-filter "git rm -r --cached --ignore-unmatch resources" --prune-empty -- --all`
   - 先在 mirror 複本乾跑驗證：改寫後 HEAD 的 tree 與真實 HEAD tree **完全相同**（`457f246c…`），
     只有 `aad5241`（只加了 style guide PDF）因變成空 commit 而被剔除。
   - `git-filter-repo` 未安裝；這個規模（74 commits）用內建 `filter-branch` 即可，86 秒完成。
4. **真正清除本地物件**：刪 `refs/original/*` → `git reflog expire --expire=now --all` → `git gc --prune=now`。
   ⚠️ 少了這一步，舊 blob 仍會留在本地 `.git` 裡（`refs/original` 與 reflog 都是可達路徑）。
5. **force push**（`git push --force origin main`）。

**結果**：全物件庫 `resources/` 命中 **0**；`.git` **77.49 MB → 11.21 MB**；
磁碟上的 `resources/` **106 檔／92 MB 完整保留**，且仍被 `.gitignore` 排除（本地作業不受影響）；
commit 數 74 → **73**。

#### O3. 兩個必須知道的副作用

| 副作用 | 說明 | 處置 |
|---|---|---|
| **所有 SHA 變號** | 改寫會重算初始 commit 之後的每個 commit 的 SHA。文件裡引用 SHA 就會被綁死 | 本輪同步更正 5 處：`ce85f55`→`37939bf`、`280bbb8`→`cfdad94`、`e0a36c5`→`0454519`（另 2 處為同值重複）。**日後引用 SHA 前先確認歷史未被改寫過** |
| **GitHub 端仍可依 SHA 查到** | force push 只讓舊 commit 變成「不可達」，GitHub 不會立刻回收；知道 SHA 的人短期內仍讀得到 blob | 使用者裁定去信 GitHub Support 請其清除不可達物件。`forks_count: 0` 是這次能安全處理的前提——**有 fork 的話，改寫本 repo 不會動到別人的副本** |

> **更徹底但未採用的選項**：刪掉 repo 重建（唯一能保證零殘留的做法，且因 `forks = 0`、`stars = 0`、
> 無 issue／PR 而幾乎零損失；代價是要重開 GitHub Pages 並重建 `gh-pages`）。
> 保留作日後若 Support 未處理時的備案。

#### O4. 給接手 session 的檢查清單

要驗證「公開 repo 有沒有不該公開的檔案」時，**三個層都要查**，只查工作樹會得到錯誤的安心：

```powershell
git ls-files <path>                      # 索引層
git check-ignore -v <path>               # 忽略規則
git rev-list --objects --all | Select-String "<path>"   # 歷史層（真正會漏的那一層）
```

使用者回報：速查手冊的「**魔能發電模組**」顯示成「魔能發 ⚡ 電模組」——
「發電」的「電」被當成閃電屬性，硬插了官方字型符號。同一個模組的說明文字本身沒問題，

#### Q2. 根因：黑名單永遠追不上語言

`FUIcon.jsx` 的 `renderTextWithAffinities` 用**一條巨型正則**判定，以負向後顧逐一排除例外詞：

```
(?<![曲暴疾])風   (?<![中劇])毒(?![素液])   (?<!微)光   (?<!黑)暗(?![影])
物理(?![防])     電(?![壓])                火(?![器焰])
```

黑名單只能擋「已經想到的詞」。`發電` 不在名單裡，於是中彈。
更糟的是**註解與實作早已脫節**：註解聲稱已避開「焦火」，但 `火(?![器焰])` 只有後顧、沒有前顧，
`焦火` 照樣被標——這個詞在速查手冊裡就真的被畫錯了。

#### Q4. 修正：情境白名單 ＋ 夾字否決

判定邏輯抽出為純函式 **`src/components/ui/affinityText.js`**（`findAffinityTokens`），
`FUIcon.jsx` 只負責把結果畫成 `<span>`。規則改為「**只有正面證據才標**」：

| 規則 | 依據 | 例 |
|---|---|---|
| R1 | 括號 | 【火】、（火） |
| R2 | 明確後綴 | 火屬性／暗屬性傷害／物理抗性／毒系傷害／電傷／物理類型 |
| R3 | 列舉串（≥2 詞，以分隔符相接） | 風、電、土、火或冰／風／電／暗／土／風土火電或冰／風弱電、電弱土 |
| R4 | 整串就是屬性詞 | 粗體切塊 `**暗**`、下拉選單值 `'火'` |
| R5 | 傷害式尾綴 | (HR + 8) 物理／【HR + 5】物理 |
| R6 | 繫詞後 | 變為土、則為暗、類型為光 |
| R7 | 編號列舉（≥2 項成串） | 1.風 2.電 3.暗 4.土 5.火 6.毒 |
| — | **夾字否決** | 屬性字右側緊接非黏著漢字 → 只是詞的一部分，不標 |

**原則：寧漏不誤。** 少一個圖示只是少一點裝飾；多一個圖示是把「發電」讀成「閃電」，是內容錯誤。
只有「成員 ≥3 且多數成員未被夾住」的列舉串能救回被夾住的成員
（例：「在電、暗、火、冰、光**中**選擇」的「光」），
而整串都是詞的情況（「風格、光環、暗影」）不在此限。

列舉串的連接詞含 **`弱`**：相性表的官方記法「風弱電、電弱土」若不含它，
就會被拆成 7 個雙詞串而全部失標。

#### Q6. 已知殘留與刻意接受的損失

- **殘留**：詞尾剛好是屬性字、後面緊接分隔符再接另一個屬性詞時仍會誤標
  （例：「貿易之風、電屬性」的「風」）。中文裡這與「受到風、電」在字元層面無法區分，故接受。
- **刻意接受的失標**（原本會標，現在不標）：`風之源泉【洞察】` 的「風」、`不屬於物理的傷害類型` 的「物理」、
  `寒冷、冰、沉默`、`火、熱、金屬`、`霧、雨、風暴`、`風元素爆發`。
  這些都是「讀起來仍然完全清楚、只是少一個小圖示」的情況。
- **仍會標且正確**：`風之源泉（風）` 的括號內、`(HR + 8) 火`、`風弱電、電弱土`、
  `在風、電、土、火、冰、光之中選擇`。

#### Q7. 教訓

1. **自然語言的判定不能用黑名單。** 判定的依據必須是**正面證據**（括號、後綴、列舉、繫詞），
   而不是「我還沒遇到過的例外」。317 處誤標不是運氣差，是方法錯。
2. **註解會腐爛。** 「已避開焦火」寫在註解裡、實作卻沒有對應的前顧——沒有測試護欄的註解等於願望。
3. **稽核腳本必須與正式程式共用同一份實作。** 本輪稽核一開始把正則**複製**到腳本裡比對，
   若兩邊不同步，稽核驗的是一份不存在的程式；改為抽出 `affinityText.js` 後，
   測試、稽核、渲染三邊才算真的同源。
4. **修完要留下可重複的關卡。** 誤標表寫進測試，下次有人想「放寬一點」就會立刻撞牆。

#### R3. 牌運亨通：三條效果不是互斥

原書：「if it includes a joker and/or a 7, you deal (SL) extra damage…; if it includes a joker
and/or a 1, all damage you suffer is reduced by (SL)…; if it doesn't include any joker, 1, or 7,
you recover (SL × 2) Hit Points.」

一組牌可以**同時**含 1 與 7（例：滿貫狀態的 3 張 1 + 2 張 7），此時「+SL 傷害」與「減傷 SL」
同時成立；只有「回復 `SL×2` HP」要求三者皆無。故狀態不是單一 enum 而是三個獨立數值
（`{ extraDamage, damageReduction, heal }`），由純函式 `highOrLowState()` 判定。

> 舊實作的問題不是算錯，而是**根本沒有地方記**——玩家只能靠腦記「這個回合我 +3 傷害」。

#### R4. 再調度：程式代替玩家丟牌（本輪修掉）

### T. 卡牌大師：小丑牌指定 ＋ 撲克牌面 ＋ 衝突結束卡死 —— ✅ 2026-10-05

使用者回報三件事：「小丑卡要有個可以自定花色和數值的功能」、「卡牌的呈現可以更像撲克牌一些」
（附 888poker hand rankings 參考圖：**數字和花色都一樣大的長方形**）、
「我點衝突結束收回之後，就再也抽不了卡了」。

#### T1. 衝突結束卡死（真 bug，先講成因）

**症狀**：按下【衝突結束（全部洗回）】後，牌桌停在「手牌已空」，**再也回不到「衝突開始」**。

**成因**：UI 的狀態判準寫成

```js
const inConflict = deck.length > 0 || hand.length > 0 || discard.length > 0;
```

而【衝突結束】的規則是「把全部 30 張洗回牌庫**並收起來**」——收起來之後**牌庫裡正好有 30 張**，
於是 `deck.length > 0` 永遠為 true。而「衝突開始」按鈕是 `!inConflict` 才顯示——
**按鈕自己把自己鎖掉了**。使用者看到的是「莫名其妙」，實際上是判準選錯欄位。

**修法**：判準抽成資料層純函式 `isDeckInConflict(data)`，並補上明確的狀態欄位：

| 情境 | `active` | 判準結果 |
|---|---|---|
| 衝突開始（`startConflict` 寫 `active: true`） | true | 衝突中 |
| 衝突結束（`endConflict` 寫 `idleDeckState()`） | false | **不在衝突中** → 顯示「衝突開始」 |
| 舊存檔（沒有 `active`） | undefined | 啟發式：手牌／棄牌堆非空，或 `0 < 牌庫 < 30` |

> ⚠️ 啟發式第一版寫成 `deck.length < DECK_SIZE`，被測試當場抓到：
> **牌庫為 0 是「還沒建立牌組」（全新角色），不是「衝突中」**——
> 那會讓全新角色一開卡就看到「手牌已空」而不是「衝突開始」。
> 正確寫法是 `deck.length > 0 && deck.length < DECK_SIZE`。
> **這正是把判準抽成純函式、並在測試裡同時放「全新角色」與「衝突結束」兩個案例的價值。**

#### T2. 小丑牌指定（原書 p.8）

原書：「When you resolve a set that includes jokers, **you** choose their suit and value (1 to 7).」
——指定權在玩家手上，而且**花色會決定傷害類型**（魔法同花／雙重麻煩的傷害類型取自結算牌花色）。

舊實作只做 `expandJokers()`：窮舉 28^n 種指定、取**第一個**成立的組合來判定。
那等於**代替玩家決定花色**——同一組 `♠3 ♠4 ♠5 + 小丑牌`，
指定黑桃 6 是【魔法同花順】（冰屬性），指定紅心 6 只是【炫目順子】。

新增：

| 函式 | 用途 |
|---|---|
| `applyJokerAssignment(cards, assignment)` | 依玩家指定把小丑牌填成具體牌 |
| `isFullyAssigned(cards, assignment)` | 是否全部指定完 |
| `suggestJokerAssignment(cards, level, opts)` | 建議一組可行指定（「套用建議」按鈕用） |
| `detectSets(..., { jokerAssignment })` | **全部指定完**才用玩家的指定；否則退回窮舉（相容） |

UI：選牌含小丑牌時出現「小丑牌指定」面板——每張小丑牌兩個下拉（花色／數值 1–7），
即時顯示「→ 黑桃 6（冰屬性）」，並在牌面上**直接顯示指定的花色與數值**。
未全部指定時面板會標示「目前由程式窮舉自動判定」，玩家知道自己送出了什麼。

#### T3. 撲克牌面

舊的彩色底牌面（`SUIT_STYLE`）整組移除。

> 副作用（刻意的取捨）：牌面不再顯示傷害類型文字，改由 `title` 提示與牌面顏色辨識。
> 參考圖上沒有這種標籤，而花色→類型對應本來就在上方的「花色對應」面板。

#### T5. 教訓

1. **「看起來是 UI 壞掉」的問題，根因常在狀態判準選錯欄位。** 按鈕把自己鎖掉，
   畫面上只表現為「按了沒反應」——先問「這個分支的條件是從哪個欄位推出來的」。
2. **把判準抽成純函式，才驗得到「回不去」這種跨狀態的 bug。** 原本的判準寫在 JSX 裡，
   任何測試都碰不到；抽成 `isDeckInConflict` 之後，`idleDeckState()` → `false` 就是一行斷言。
3. **規則要求「玩家指定」時，不要用「窮舉後取第一個成立」代替。** 那不是實作等價，
   而是把玩家的決策權換成了程式的任意選擇——而且會靜默改變傷害類型。

#### U5. 呈現設計（本輪的研究結論）

**核心判斷：要讓玩家「一目了然選到最想要的裝備」，關鍵不是把選項排整齊，而是把選項換算成「對這個角色而言的結果」。**

原書的裝備表寫的是規格：`HR + 14`、`DEX + MIG`、`先攻 -2`。但規格本身不可比較——
同一把戰斧，體魄 d12 的角色期望傷害是 **22.5**，d6 的角色是 **18.5**；
同一件賢者長袍，敏捷 d6 與 d10 的角色物防差 4 點。原書把這件事寫在說明文字裡（p.127：
「物防／魔防取**當前**骰尺寸」），表格卻看不出來。玩家只能心算——而心算不會「一目了然」。

因此三條呈現原則：

1. **顯示後果，不顯示規格。** 每一列都即時換算成該角色的數字：
   期望命中（兩顆屬性骰之和 + 命中加值）、期望傷害（**HR 期望值** + 傷害加值）、
   合計物防／魔防、先攻。期望值是精確解，不是估算——
   `E[max(d8,d6)] = 251/48 ≈ 5.229`，用 `Σ P(X > k)` 疊加求得，測試再以暴力枚舉獨立驗證。
2. **不能選的原因要在選之前看見。** 熟練度不足、超出 500z 預算、雙手武器佔滿手部——
   全部標在列上並降低透明度，而不是選完才跳警告。原介面只有一個「選完才出現」的警告框，
   而且它用的還是舊譯名「軍用」（違反定譯鐵律「職業」）。
3. **比較要對齊欄位，所以用表格而不是卡片牆。** 卡片好看，但看不出誰的期望傷害高；
   表格可以按期望傷害排序，並用一條相對長條把差距視覺化。

副手另外處理：**「盾牌」與「單手武器」是兩種完全不同的比較基準**（前者比合計防禦、後者比期望傷害），
所以拆成分頁而不是混在同一張表。盾牌表直接顯示「穿上後合計物防／魔防」，而不是盾牌自己的 +2。

#### U9. 教訓

1. **「一目了然」的瓶頸是換算，不是排版。** 先問「玩家要比較的是什麼數字」，
   再決定用什麼元件呈現；反過來做（先挑元件、再往裡面塞資料）只會得到一個漂亮但沒用的選單。
2. **把權威寫成斷言，才會抓到人工複核三次都漏掉的錯。** U3 的三個類別錯誤，
   人工看過三遍都沒發現，測試一跑就現形。
3. **`JRPGModal` 以掛載後的 effect 為閘門，SSR 時不渲染 children。**
   所以任何要測的彈窗內容都必須抽成獨立元件（本輪把 `EquipmentPickerBody` 拆出來），
   否則「彈窗渲染煙霧測試」會拿到空字串——**一個永遠通過的測試等於沒有測試**。
4. **來源不明的資料不要順手刪——但也不要永遠留著。** 三筆查無出處的武器已進入官方配置與既有存檔，
   刪掉會靜默改變別人的角色卡；可是留著就是一份沒有依據的資料。
   正確順序是：**先釘住現況 → 追出處 → 拿到裁定才動手**。
   U4 的第二輪就是這條的完整示範：`git log -S` 一路追到 repo 的第一個 commit，
   從「同一批種子的其他數值全都錯」反推它不是照抄原書，才敢下定論。
   **「找不到」本身不是理由，「查過所有可能來源都找不到」才是。**

#### U11. 裝備圖示對照表：從使用者的設計器反推 game-icons 名稱

使用者指出設計器各分頁**左上角的 IMAGE() 公式格**就是他的圖示來源（全部由 game-icons 匯出）。
該公式是一長串巢狀 `IF(原型=…, IMAGE(https://i.imgur.com/….png))`，
共 **18 個武器原型 + 10 個盾牌防具原型**。

問題：imgur 連結不含圖示名稱，無法直接對應到 `react-icons/gi` 的元件。
本機也沒有任何 SVG 光柵化工具（無 ImageMagick／Inkscape／cairosvg；LibreOffice kit 明確拒絕 svg 輸入）。

**解法（可重複、客觀）**：

1. 以 `react-dom/server` 把 **全部 4,036 個 `react-icons/gi` 圖示**輸出成 SVG（`scratch/gi_all/`）。
2. 自寫 `scratch/svg_raster.py`——極簡 SVG 路徑光柵器（M/L/H/V/C/S/Q/T/A/Z、弧線轉三次貝茲、even-odd 填色），
   把每個圖示畫成 256×256 遮罩。
3. **先剔除右下角的職業徽章**：設計器的圖示把「✦ 職業」徽章直接疊在圖上，
   它會被算進內容邊界，導致整張圖縮小偏移——**這是第一輪比對失敗的主因**（多數 IoU 只有 0.3～0.5）。
   改為用連通區塊分析移掉「位於右下且面積遠小於主體」的區塊後，分數立刻跳到 0.8～0.98。
4. 裁到內容邊界 → 等比縮進 96×96 → 以 IoU 取最高分。

#### U12. 守護者【雙重盾牌】

原書（`rulesData.json` 守護者技能）：
> 你現在可以在你的主手欄位裡裝備盾牌了。只要你裝備了兩個盾牌，你就可以同時獲得這兩件物品的好處，
> 並可以將它們合併視為以下格鬥類別的雙手近戰武器：
> **雙盾**：命中【MIG + MIG】，傷害【HR + 5】物理傷害；額外造成等於你在《防守掌握》中的【SL】點傷害。

實作要點：

- `DUAL_SHIELD` 是一筆**虛擬武器條目**（格鬥／雙手／近戰／`MIG + MIG`／`【HR + 5】物理`），
  所以它能直接餵進既有的 `evaluateWeapon`——不需要為它開第二條換算路徑。
- `getDualShieldState(character, { mainIsShield, offIsShield })` 回傳
  `{ learned, active, defenseMasterySL, weapon }`；`active` 只在**兩手皆盾且已學會技能**時成立。
- `checkEquippable` 現在會**依 `defBonus` 欄位自動認出盾牌**，
  因此盾牌擺在主手時吃的仍是「職業盾牌」熟練度（不是職業近戰武器）。
- `buildLoadoutIssues`：主手放盾牌但沒學技能 → 明確報錯；
  學了技能且兩手皆盾 → **不算持握衝突**。
- `CharacterPlayHUD` 的主手攻擊也走同一份判定，跑團卡顯示的命中與傷害與裝備頁一致。
- 額外的《防守掌握》SL 傷害**只顯示、不塞進傷害式**——`parseDamage` 只讀 `HR + N`，
  把 SL 硬塞進字串會讓解析器說謊。裝備頁以文字註明「額外 +N（防守掌握 SL）」。

#### U13. 第二輪教訓

1. **統計量不是規則。** 期望值能讓「哪把打得痛」可比，但它不是書上的數字，
   玩家得在兩個體系間換算——這與「一目了然」的初衷相反。
2. **預設值就是預設答案。** 「顯示全部、讓玩家自己挑掉不能用的」與
   「只顯示能用的、要看得自己打開」在資訊量上差了一個篩選動作；後者才是預設。
3. **對照外部圖示時，先處理浮水印／徽章再比對。** 一個右下角的小圓徽章足以讓 IoU 從 0.95 掉到 0.35，
   而且會讓「最像的」變成完全無關的圖示（如 `GiClaw`）。**先質疑前處理，再質疑資料。**
4. **能自己寫工具就不要放棄。** 本機沒有 SVG 光柵器，但需求只是「把 path 畫成點陣」——
   100 行的弧線轉貝茲＋even-odd 填色就解決了，而且之後可重複使用。
